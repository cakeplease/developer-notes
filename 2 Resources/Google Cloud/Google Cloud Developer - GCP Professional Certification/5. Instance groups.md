**Instance groups** are a collection of VM instances that can be managed as a single entity.

#### Two kinds

- **Managed instance group (MIG)** - identical VMs created from an #instancetemplate 
	- **Maintain instance count** - keep constant number of VMs running all the time
	- **Self healing** - use health checks to spot and fix app failures
	- **Auto-scaling** - automatically add or remove VMs depending on the load
		- **Minimum and maximum number of instances**
		- **Metrics**: CPU utilization, load balancing utilization, cloud monitoring metrics
		- I**nitialization period** (cool-down period): how long does your application need to initialize? Time that allows proper application start up before health checks
		- **Scale-in controls**: avoid sudden reduction in instances, ex: limit scale-in to 10% or 4 instances in 5 minutes
	- **Load balancing** - distribute traffic across healthy VM instances in MIG

Two kinds of managed instance groups: **stateless** and **stateful**
#stateless - Automatically manage groups of VMs that do stateless serving and batch processing
#stateful - Automatically manage groups of VMs that have persistent data or configurations (**such** as databases or legacy applications)

- **Unmanaged** - VMs with different configurations

#### Zonal or regional

- **Zonal** (single zone) - all VMs in one zone
- **Regional** (multiple zones) - spread across zones in one region for higher availability (preferred)
	- MIG: create instances in multiple zones in a single region:
		- **Rolling updates** - release new version gradually. Update a percentage of instances to the new version at a time.
			- Specify new template
			- When to update: automatic (pro-active) or selective (opportunistic - when instance group is resized later)
			 - How to update:
				 - Max surge: extra instances during update
				 - Max unavailable: instances allowed to be down during update
		 - **Canary deployment** - test new version with a group of instances before releasing it across all instances.
